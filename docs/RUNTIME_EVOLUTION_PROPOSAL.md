## 0. 当前工作指南：先补核心能力，再做发表评估 — 2026-11-04

### 0.1 先学同行如何获得能力，不先比较分数

本轮转向可借鉴的能力机制，结合论文方法和作者开源实现；不把README宣传当作已经复现的稳健性，也不把现有仓库能力倒推为首版预印本能力。学习机制、工具与文档组织，不复制其Agent框架或把别人整套系统接成我们的内核。

### 0.3 适合我们的最小方案

保留Native Kernel与用户级本地Apptainer，优先补**“有资料支持的自主执行＋基于实际结果的核查纠错”**，而非新增完整框架。

- **知识／工具层**：接通现有Skill发现和正文阅读、环境事实、官方API用法；先复用现有Gold、库内帮助及科学库，确有缺口再接现成文档检索工具，不为RAG单独建设大型基础设施。需要外部组件时先核对许可、版本和可接入边界，不把同行整个框架变成必需依赖。
- **行为层**：Agent自行拆解当前问题、提出可检验的小目标、保留失败原因与下一步；领域经验放在可读、可拒用的外部Skill／profile。资料提供条件和用法，不替当前任务选定科学方法、参数、程序或答案。
- **协作层**：复用同步`delegate`，最小先做“执行负责人＋可选核查Specialist”；是否委派由Agent判断，不强制每步固定多Agent。双方要能读取被授权的实际程序／产物，而不是只互相读总结。先修App组装和工具归属，不等待持久异步队列。
- **执行层**：所有诊断、分析、校验程序和环境构建仍经原受管接口；必要的独立计算由运行Agent提出、编写并执行。优先采用核查建议→原执行负责人受管运行→核查者读原结果的最小路径，不能给只读角色偷偷增加执行权限。
- **上下文层**：复用笔记／观察／Artifact，保留当前目标、已确认事实、失败尝试、未决问题和确切中间产物；Agent自行维护，宿主只管身份、保存、授权和有界回读。不新造第二套知识／任务数据库。

不能先验保证多Agent更强。若单Agent加准确工具知识已能解决问题，不为追求架构形式多加角色。若强模型在清晰接口下才稳定，明确这是模型依赖；开发时可公开调整模型／通用profile，不能自动切换模型或把模型错误全归于runtime。

### 0.4 当前阶段目标：A0—A3能力建设

以下是研发阶段，不是正式benchmark；当前不锁定12题、32次或排名指标，也不以缩小论文主张替代本应做的能力优化。

| 阶段 | 重点工作 | 如何判断真的补上，而非只加接口 |
| --- | --- | --- |
| A0：同行机制与真实App能力盘点 | 按知识、执行、纠错、核查、上下文、协作逐项对照；查日常App实际profile／工具／peers／环境，不只看内核类 | 给出已接通、缺失、尚不稳定的证据及最小改进点。本轮完成初步源码盘点和同行机制学习；真实调用行为不因此算通过 |
| A1：会查、会用、会修 | 主攻陌生Python库／API：资料发现与阅读、已安装版本／可用环境、新依赖构建、实际报错、Agent修订及重验。复用已有执行和构建链 | Agent面对非预写用法问题，能实际查证、选择环境、读取诊断、修改自己的程序并交付结果；原错误及修订轨迹保留，邻近任务也可用，不能由Codex给正确代码／参数 |
| A2：会质疑并核查结果 | 在App接通最小同步协作；核查者读取实际程序和关键结果，提出可执行检查；利用已有VALIDATE→EXECUTE或阶段内委派闭环，不重建Workflow | 对“程序退出0但结果不可信”的反例，Agent能发现矛盾、得到新检查证据并自主修正或限制结论；正常邻例不被乱改。仅口头同意、文件非空、另一Agent评分不算闭环 |
| A3：能连续完成真实多步分析 | 把A1／A2用于已有H5AD／多文件需求；检查实际中间产物复用、失败后继续、用户追加要求及报告忠实性，按暴露的最早根因收敛 | 不由人工代写或代调科学程序完成多步交付；关键结果可核查、报告对应实际执行。单次成功只算案例，需相邻需求／独立复跑确认不是专用补丁；此时再决定正式实验的范围 |

**A1历史验收见第0.6—0.9节；当前A2／A3按第0.10节合并实施和验收，不先设计正式排行榜。**第0.10节优先于更早的“A2未实施”历史记录。

研发验证的做法：

1. 使用真实小规模分析需求定位能力缺口，不为评测先预写一套科研程序。工程故障可用最小合成夹具复现；科学求解、库／参数／修订仍由运行Agent完成。
2. 每个改进追到模型实际所见→决定／工具参数→校验／执行→证据→下一动作。修最早失真的边界，保留失败反例和合法邻例；不能只堆同义提示、自动补参数或增加无依据的重试。
3. 给必要调查、代码生成和纠错留出合理预算，不用过低上限人为制造失败，也不静默扩资源。按一批能力目标约定费用／时间边界，在授权内连续推进，不每个小修就重新征求续跑；未知副作用、权限变更、预算超限仍停在真实边界。
4. 没有新证据的同类失败先诊断，不反复烧模型；有新证据可由Agent继续调查、改方法或修程序。技术通路正确但模型失败时，分析能否由更好的资料、上下文或核查机制一般化改善，不能一概归为“模型错误所以不优化”。
5. 失败记录、人工介入、版本差异和未知用量全部保留。研发期间允许逐步改进，但不得把挑出的最终成功冒充冻结正式测试；定量发表实验另划保留任务。

### 0.5 发表评估后置，但不无限扩建

A1—A3补上最主要能力并形成真实运行证据后，再收敛论文贡献、选择公平基线、确定正式任务／重复／预算，整理独立科学审阅和公开复现材料。此前的32次方案不再是默认执行协议。论文定位要随实际形成的能力决定，不先把系统限制成“只做审计、不解决分析问题”。

仍暂缓完整R3持久异步、R4 Monty、DBOS默认App／完整云模型冷恢复、多节点／断电及全面部署矩阵；**最小同步协作与核查能力不能因为暂缓R3而一并不做。**原R5正式对照放在能力建设之后，不再作为眼前主线。

不追求全组学、全语言、全宿主、零错误再发表；也不因赶预印本跳过核心能力。原始数据／执行、权限、预算、停止、证据和用户级Apptainer边界保持；Docker／Slurm不自动替代。科学正确性不由宿主硬编码，最终仍需独立审阅。

以上初始路线修订仅调研、源码只读核对和指南纠正；之后获授权的A1实施见下节，不改写该历史盘点。

## 1. 建议结论

保留我们自己的 Native Kernel，演进为**具有持续工作状态、可恢复动作和受限异步协作的 Agent runtime**。不再接一层完整 Agent Harness，不重新实现通用耐久调度器、解释器、追踪服务或外部工具协议。

复杂问题的能力提升，应来自 Agent 能保留调查进展、看到真实错误、继续原来的子任务、核查自己的结果，而不是平台预写更多科研流程或不停增加 Agent。

明确选型：

- **保留**：Native Agent loop、Workflow 生命周期、权限与预算、五种 provider 格式、Artifact/Observation、真实读取凭据、JobLedger；执行主路径及兼容边界按下节约束。
- **直接复用方向**：OpenTelemetry 追踪；需要外部连接器时使用官方 MCP Python SDK。只接所需部分，不为已有内部工具增加网络层。
- **耐久调度首选原型**：DBOS，限定在阶段内部的模型回合和受管动作边界；不是把整个阶段交给它自动重跑。先做故障验证，通过后才接入正常运行。
- **代码化查询首选原型**：直接使用 Monty，而不是自建 Python 解释器或为此引入整个 PydanticAI Harness。初期仅开放已有受控只读查询。
- **暂不采用**：整套 LangGraph/Deep Agents/PydanticAI Harness 替换、托管 Agent 控制面、Temporal/AX 集群基础设施、无实际需求的向量库、自动模型切换。

其中组件适配和采用顺序是本项目的工程判断，不是上游对 LabBioAgentOS 的性能承诺。DBOS 最小隔离原型已通过第23节验收，正常App集成尚未验收；Monty尚未验证，均未接入正常runtime。以下保留长期工程设计，当前发表优先级以第0节为准。

### 1.1 已确定的沙盒技术路线：用户级本地 Apptainer

用户已明确确定：**用户级本地 Apptainer 是 App 的默认执行主路径，不是临时试验后端。**
App 与 non-setuid Apptainer 均面向普通用户安装、调用，不以 sudo、系统包安装或管理员配置作为标准安装步骤。

- 后续 runtime 开发、真实任务和纠错验收以该主路径开展。遇到安装、环境构建、运行、错误反馈、资源限制或取消问题，沿此方案定位并修复根因；不得为通过测试切回 Docker、提交 Slurm，或静默撤掉保护。
- Docker 和 Scheduler＋Apptainer／Slurm 仅保留显式选择的兼容方案；缺配置、依赖或宿主能力时明确拒绝，不自动回退。兼容方案另行验收，不替代主路径验收。
- 默认普通用户模式采用 `systemd-affinity`：锁定正整数逻辑核集合，保留 memory／pids 硬限制、禁 swap、超时及整棵进程树生命周期。它不是小数 CPU 带宽配额，也不是独占核；需要 CPU controller 的严格 quota 模式保持可选。
- 无 sudo 不代表绕过宿主政策：仍依赖宿主允许所需 namespace、可访问的 systemd 用户管理器及 memory／pids 委派。能力不足时记录明确边界，不扩大资源或假称限制已生效。

本决策不改写历史 Docker／Slurm 运行，不自动迁移外部配置或激活生产 Release。具体安装步骤见 [USER_INSTALL.md](USER_INSTALL.md)。

### 3.2 不止 Multi-agent：真正值得组合的机制

1. **持续工作状态**：Agent 维护进展、尚未解决问题、已失败尝试及证据位置；新上下文能继续工作，而非重新猜测。Anthropic 长任务实践也明确指出，只有 compaction 不足以解决长期任务连续性。[长任务 Harness](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
2. **按需协作，而非 Agent 越多越好**：独立查询和反例检查可以分开；紧耦合修改仍由同一个负责 Agent 推进。Anthropic 自己也指出多 Agent 的 token 成本明显上升，不能直接把其内部评测收益外推到本项目。[多 Agent 的收益与代价](https://www.anthropic.com/research/multi-agent-research-system)
3. **可执行的核查，而非纯口头反思**：审查 Agent 要实际读程序、核对结果或执行独立反例；“另一个模型说没问题”不等于科学正确。
4. **分层恢复，而非统一重试**：传输重试、模型纠正参数、程序修改、用户解除停止不是同一种操作。PydanticAI 也把这些层次分别处理，并警告叠加重试会相乘。[重试机制](https://pydantic.dev/docs/ai/core-concepts/retries/)
5. **程序化处理受控中间结果**：让 Agent 用短程序处理循环和选择，不让模型每次都重读原始中间表；每个底层调用仍由宿主授权和记账。[Programmatic tool calling](https://www.anthropic.com/research/advanced-tool-use)

## 4. 目标架构与责任边界

```text
用户 / 项目权限
       │
现有 WorkflowEngine                 唯一的阶段、暂停、审批和完成状态权威
       │
Native Leader loop                  Agent 自主选择问题、方法和任务分工
       ├── 工作笔记 + 所选证据交接    笔记由 Agent 写，原始观察继续完整保存
       ├── 持久 Specialist 任务       启动 / 查询 / 取结果 / 续问 / 取消
       └── 受管工具派发
                  │
       Native 权限 / 预算 / 动作回执   唯一的动作效果与证据权威
                  ├── Artifact / Observation / JobLedger
                  ├── Local＋用户级 Apptainer（默认主路径）
                  ├── Docker / Scheduler＋Apptainer（显式兼容，不回退）
                  ├── MCP SDK（实际需要的外部连接器）
                  └── Monty（后续只读组合查询原型）

DBOS 原型：承接阶段内部的耐久调度游标与已存步骤引用，不决定业务终态
OTel：从现有追踪导出父子调用与安全诊断，不替代审计记录或外发原始数据
```

### 4.1 持续纠错：给 Agent 足够的事实，不替它选答案

- Agent 自行维护有版本的简短工作笔记：当前判断、未解决事项、失败尝试、下一步意图和证据引用。宿主只校验权限、来源和大小；不要求写隐藏思维链，不生成科研计划。
- 把已有错误整理为一致的受控诊断：失败层、字段路径、退出码、容器可见工作目录/挂载或受控路径别名、程序与环境版本、可读日志引用、是否已产生副作用、剩余预算。只呈现已知事实，未知仍为未知，不把宿主绝对路径加入模型上下文。
- 对同一调用身份、同一参数和未变化的环境/证据，显示重复失败次数；Agent 决定换方法、查文档、安装库或缩小问题。现有总预算继续兜底，不增加无限“反思”或隐藏 fallback。
- 环境构建失败，返回真实安装诊断；分析程序失败，返回真实执行诊断。平台修的是错误信息或执行契约；科研依赖、程序和分析策略仍由运行中的 Agent 修。
- 交接大小和已选证据占用在运行中可见；Agent 可逐步维护交接选择。超限反馈具体项目，不删空证据后仍让 finalizer 判断。
- 归档历史、Agent 笔记和交接证据是三种不同身份：笔记不自动成为原始证据，跨阶段引用必须把实际内容交给当前 Agent。

### 4.2 受限异步协作：先持久，再并行

- 先把现有 TaskBoard 的任务身份、父子关系、输入、状态、子历史引用和终止原因持久化；复用已有存储/执行记录，不新建通用 DAG 引擎。
- 在兼容同步 delegate 的前提下，提供任务启动、状态、等待、结果、取消、继续原任务的最小接口。名字在实现时沿用项目风格，不先发布多套同义 API。
- Leader 自己决定是否委派、找谁、何时续问；不由 Codex 预选科研 Specialist，也不通过错误关键词自动路由。
- 初始最多两个活跃子任务，共享根任务的模型、工具、CPU、内存与时间上限；并发前做原子准入，实际用量照实累加。不能让每个子任务各自获得整份根预算。
- 停止信号传至子孙任务及其分析进程树；用户停止后不能由 Agent 自行重新启动。恢复必须满足现有显式授权和版本规则。
- 先保留当前精确 provider/model 绑定。异构模型 profile 等协作稳定后另审，不把隐式模型切换混入本轮优化。

### 4.3 细粒度恢复：DBOS 只负责通用调度

DBOS 默认支持本地 SQLite；多服务器部署需要另行评估 Postgres，不能把共享盘 SQLite 当分布式数据库。[数据库边界](https://docs.dbos.dev/python/tutorials/database-connection)

原型切在真实边界：模型调用结果持久化 → 受管工具调用意图 → 实际副作用对账 → Native 回执提交 → 模型接收结果。Agent 的动态选择可以保存为步骤结果，但不把整个科学阶段包进一个自动重试步骤。

必须满足：

- DBOS 步骤仅返回 Native 的 `receipt_id`、哈希和受权读取引用；已有 JobLedger/ObservationStore 是动作效果和证据的权威，不再建第二份可变业务状态。
- 稳定调用身份必须在副作用之前确定并绑定请求哈希；同一身份不同参数必须拒绝。接管时须撤销旧 worker 的有效写入权限，防止旧、新 worker 同时提交；只取消协程不够。
- Native 已存回执、DBOS 未存完成：从 Native 读取原回执，禁止重执行。
- DBOS 已存完成、Native 对应记录缺失或哈希不符：阻断核对，不能凭调度框架的“完成”提升运行终态。
- 工具提交已生效但回执未存：用稳定调用/作业身份查询执行端；只能返回已知结果、继续等待或明确阻断。不能把“没找到本地回执”解释成“没有执行”。
- 模型请求可能已计费但响应未存：保留未知用量与不确定结果，不由自动 replay 隐藏重复成本；后续请求仍受现有预算和重试权限约束。
- 不对权限拒绝、非法科研程序或未知副作用做框架级自动重试。DBOS 未完成步骤可能重跑，外部执行并不因此获得 exactly-once。[耐久步骤语义](https://docs.dbos.dev/python/tutorials/workflow-tutorial)
- 框架取消不等于进程取消：DBOS 默认在下一步前停，async preemptible step 也不自动清理外部进程，仍须 Native launcher 收敛整棵进程树。[取消语义](https://docs.dbos.dev/python/tutorials/workflow-management)
- 绑定源码、schema、执行环境与模型配置版本；不跨版本硬恢复历史 run。[版本机制](https://docs.dbos.dev/python/tutorials/upgrading-workflows)

原型先覆盖一个 provider 回合和一个假工具，再接一个现有执行适配器。退出条件：如果必须重写 Coordinator/阶段主循环、让 DBOS 接管 Workflow 终态、绕开未知副作用阻断、增加单机用户必需的独立控制服务，或不得不维持两套业务真相，则停止集成并报告不适配；取消后不能证明进程树收敛、旧 worker 仍能提交或适配代价明显超过复用收益，也不能验收。不能为了完成选型再写一个自有通用恢复引擎。原型失败期间保留当前安全阻断，不声称已有无损恢复。

### 4.4 代码化工具编排：复用 Monty，但不扩大数据权限

Monty 是独立开源解释器，支持宿主函数和资源限制；它不是可任意导入科学库的完整 CPython 环境。不要用它替换科学计算容器，也不购买托管服务才能做这个原型。[官方说明](https://pydantic.dev/docs/monty/get-started/)、[限制](https://pydantic.dev/docs/monty/limitations/)

- 仅给 Agent 暴露其当前有权限的只读查询函数；不挂载原始数据、宿主文件、环境变量、网络或控制面凭据。
- 循环、筛选和查询组合由 Agent 写；宿主不代写聚合策略。构建、作业执行、报告提交等有副作用能力不纳入第一版。
- 每个嵌套查询继续通过 Native 校验、预算、取消和来源记录，不能把外层一次调用当作底层无限免费调用。
- **代码访问过结果，不等于模型逐行看过结果。** 保留原始调用记录及真正返回模型的内容清单；Agent 计算出的摘要登记为带来源关系的派生产物，不获得“整表已读”凭据。
- 原型验证 Python 宿主兼容性、解释器资源上限、底层工具超时/取消和上下文体积收益。无收益或不兼容则不接入，不改成不受控的 `eval/exec`。

### 4.5 观测与外部工具：复用标准生态

- 使用 OpenTelemetry 的 API/SDK 和可选 OTLP exporter，为 run、子任务、模型请求、工具、构建、执行和交接关联 span；复用现有查看器，不自己造追踪 UI。[Python instrumentation](https://opentelemetry.io/docs/languages/python/instrumentation/)
- 默认只导出身份、耗时、请求大小、已知/未知用量、安全错误类别和证据引用，不外发 H5AD、患者信息、完整模型正文或密钥。Native RunTrace 继续作为审计依据。
- GenAI 语义约定仍在演变，应固定版本并保持适配层，不把第三方 span 字段作为 Native 持久契约。[当前约定仓库](https://github.com/open-telemetry/semantic-conventions-genai)
- 新增外部工具时复用官方 MCP SDK；服务器声明的 read-only/idempotent 提示不是权限或可重放证明。调用仍须经过 Native 的项目、run、工具和数据暴露授权。[官方 SDK](https://github.com/modelcontextprotocol/python-sdk)、[工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

## 5. 分批实施与验收

本节保留原R0—R5工程路线和历史验收定义；2026-11-04起，当前按第0节A0—A3先补核心能力。最小同步协作前移A2，完整R3／R4继续后置；R5正式对照在能力闭环后另定，下列旧重复建议不直接授权新的付费运行。

每批都是最小源码修改、失败反例和邻近合法状态回归；不新建工作树，不顺带重构，不改用户本地配置，不自动切生产。

| 批次 | 交付 | 验证 |
| --- | --- | --- |
| R0：定位成本和事实反馈 | 按请求统计消息、工具声明、输出 schema、观察与交接大小；从现有 trace 导出 OTel；核对重复错误的实际 model-visible 入参 | 字节与 token 分开；未知用量不归零；诊断无敏感值；不改变原运行结果或调用权限 |
| R1：持续工作上下文 | Agent 自写笔记、按需回读、增量交接容量反馈；只去除经测量确认的重复内容 | 归档不丢失；笔记不能冒充证据；相同错误后 Agent 实际看到可用诊断；finalizer 不恢复工具权限 |
| R2：DBOS 最小恢复原型 | 一个模型回合与假工具，验证通过后再接现有执行适配器及 JobLedger/ObservationStore | 覆盖下述故障窗口；既不重复副作用，也不凭 DBOS 状态凭空认定完成；验证不需新增必需服务 |
| R3：持久异步 Specialist | 任务状态、恢复后的继续调查、最多两个活跃子任务、共享预算、取消树 | 父子历史隔离；工具与模型身份不漂移；结果引用可实际读取；超限和用户停止无残留进程 |
| R4：Monty 只读查询试点 | 直接复用解释器，组合已有受控查询；科学计算仍走现有容器 | 嵌套调用均授权/计费；无原始数据旁路；输出范围凭据真实；成本无改善则退出 |
| R5：冻结版本真实对照 | 在相同模型、输入哈希、权限、资源与预算下，验证复杂任务和自主纠错 | 工程完成、有效交付、科学审查分别报告；全量回归不退化；所有失败和人工介入保留 |

R2 的确定性故障窗口至少包括：模型返回后未持久化、调用意图已存但未提交、执行端已接受而回执未存、Native 回执已存但调度步骤未完成、调度完成而证据不可读、批内停止、子任务取消、执行控制进程退出、旧版本恢复、未知计费用量。各窗口同时测试其邻近合法恢复状态。

R5 先选小规模有区分度的任务，而不是无边界延长旧压力测试：

1. 简单任务：验证相同正确产物下的 orchestration 成本；用当前五整数例子作描述性参考，重新冻结的运行才作正式前后对照。
2. 新依赖/真实错误：Agent 自行配置库、读取构建和执行诊断并修自己的程序；不由 Codex 隐藏修复科学脚本。
3. 复杂证据与独立核查：多文件或长表任务，Leader 自主选择是否委派；核查 Agent 实际读程序和结果，报告保留分歧及限制。
4. 故障注入恢复：单独验证提交、回执、重启和取消窗口；不能把执行层重放算成新的 Agent 自主成功。

开始真实对照前固定重复次数与总预算，先以每类三次为建议，不预支无限续跑授权；最多两个任务并发，不静默加 CPU、内存或 tokens。旧压力测试的失败、版本、暂停状态不改写、不算作新版本成功。

新一轮内核前后对照统一使用用户级本地 Apptainer，冻结同一后端、基础 SIF 和资源模式；Agent 自建环境作为单独场景记录其声明与镜像哈希。历史 Docker 结果仅作描述性参考，不与后端迁移混作内核优化收益。

记录完成率、首次有效执行/交付率、纠错调用数、重复失败数、provider 请求数与体积、已知/未知用量、构建次数、执行修订、最终产物哈希、恢复重复副作用和残留进程。报告中同时保留：

- **工程验收**：权限、预算、取消、持久化、回执、交付是否符合契约。
- **任务验收**：用户当前要求是否实际完成，不用流程终态替代产物。
- **科学审查**：计算、统计单位、解释边界及反例核查结果；未做就是未做。

### 已实现的范围

- R0 请求计量：公共消息、工具声明、输出 schema 和 envelope 分项严格相加；实际 wire 总量单列，未知为 null，不估算 token。五个 provider 沿用原有载荷与传输，没有新增重试层。

- R1 工作笔记：`working_note_write` 保存 Agent 原文和显式来源，`previous_note_id` 创建不可变版本链；`working_note_read` 按精确 UUID 回读。复用 ObservationStore，不增加第二套笔记数据库，不自动挑选“最新”文件。Agent 必须在交接中保留需要继续使用的精确引用；尚无自动发现或子任务自动恢复。
- 笔记始终是 MODEL_CONTEXT。保存、读取、归档回读和交接检查已声明的来源依赖与当前授权，包含前序版本及 note/evidence-read 包装；不授予底层来源已读凭据。遍历上限为 256 个观察，超限显式拒绝。它不验证 Agent 笔记中未声明的事实，也不证明科学正确性。
- R1 `handoff_status`：运行中查询所选正文和最终化控制包的占用、逐项大小、余量及超限项；明确不包含当前回复、后续完成正文或完整 provider 请求，不代选证据。
- R1 重复诊断投影：已有 Agent 选定交接且控制包确实超限时，可省略控制元数据中的重复 `error_details` 全文，保留全部调用身份、状态、错误码及关联 ID，并明确列入 `omitted_item_fields`。完整归档、原 Bundle 和选中正文不变；没有交接或仍不可约超限时继续阻断。
- 默认本地 profile 更新为 `local-v5`，仅向原有 capability 阶段提供这些可选工具；自定义 profile 不被静默扩权，finalizer 仍无工具。

## 21. R2取消与本地安全接管原型 — 2026-11-03

用户授权按下一步行动，继续既有`prototypes/dbos_r2/`，不把此前原型11个绿灯当作恢复安全。先在新证据目录复跑原11项，仍复现DBOS CANCELLED但同步步骤继续写Native回执；这是上游协作式取消语义，不是要改写DBOS的缺陷。[官方取消说明](https://docs.dbos.dev/python/tutorials/workflow-management)

顺着接管事实链发现两个宿主契约缺口：`find/attach`把管理器查询失败当成服务不存在；终止确认仅检查inactive/failed，没有证明旧写者退出。12项新反例先失败、5项邻近合法状态通过。最小根修限定在既有SystemdLocalLauncher：只有明确not-found才作不存在，查询失败保持unconfirmed；终态须MainPID=0，且ControlGroup已撤销、内核已删除或cgroup.events明确populated=0。不可读、仍有进程及非法group不予确认，不先reset-failed掩盖残留。既有测试仅补真实必需的MainPID／ControlGroup事实，原合法行为不变。针对性67项及全量3293passed／82skipped通过；Native Kernel本体哈希不变。

新增隔离`controlled_round.py`复用既有用户级systemd launcher与run_writer：controller持锁，每次按规范化运行目录取得稳定service身份，先收敛旧单元，确认后才启动替代worker。锁持有者是controller，不能只因锁可取得就推断worker已退出。服务继承原4逻辑核锁定、4GiB memory、128pids及生命周期约束，不装系统软件、不要sudo、不退回Docker，也不增加用户必需的独立服务或分布式epoch引擎。清理失败就阻断，后续入口仍须处理该稳定旧单元。

实际隔离测试包括：DBOS取消后同步writer及setsid／忽略SIGTERM的子writer仍活着 → 调用既有launcher收敛整树 → 两旧writer消失 → 新writer持锁落回执 → 放开旧写入门后仍无旧回执；另测controller os._exit(75)后，新controller先收敛孤儿再启动。它们证明本地进程所有权边界，不是恢复已取消的真实Workflow，也不是活worker的分布式写权限撤销。新原型自审另留重复取消提前释放锁、目录`..`别名产生不同服务身份的失败反例；分别改为等待同一清理操作及使用规范路径身份。缺失／损坏Native观察、已存回执但未存DBOS checkpoint、pre/post-acceptance未知状态、声明request/version变化等继续按真实证据拒绝或复用，不静默重试。

执行层单列复验真实本地systemd／用户级Apptainer6项通过，包含整树取消、超时、控制进程死亡、继承限制及容器隔离。它们是已有执行层的工程回归，**不计作DBOS与真实ToolExecutor集成、Agent独立分析或科学验证**。本轮零模型请求，不替Agent选方法、程序、引用或报告。
